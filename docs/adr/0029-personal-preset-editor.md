# ADR 0029 — Personal preset editor and persistent representation defaults

Status: Owner decision on 2026-11-21 ("both, in that order": connections view first, this second). It implements the accepted [information architecture](../ux/information-architecture.md) "Prompt presets" paragraph — **Edit preset…**, **Save as new preset…**, named personal presets in user settings, and the "last compatible choice" default — without changing how prompts are composed, how intent is recorded, or what one submission sends.

## Decision

The main panel's Representation row gains **Edit preset…**, which opens an editor exposing the selected preset exactly as the architecture describes: name, short description, editable representation instructions, and — collapsed but not hidden — the preservation-intent and vegetation-policy fields that the shared geometry-preservation objective always extends. A supplied preset cannot be overwritten: it is prefilled as the starting point, and saving creates a *named personal version* while the supplied preset stays in the list. A personal preset can be saved in place, copied with **Save as new preset…**, or deleted behind an explicit one-time confirmation; personal presets live in one JSON document in the user's application data (`…/VisoLoom/presets/personal.json`, read and written with the same fail-closed discipline as the durable image store), deliberately outside `.3dm`, project settings and Git. Revisions are stamped by the store on every save, so a job's recorded `PresetId`/`PresetRevision` keeps distinguishing edited generations, and editing or deleting a preset can only affect submissions made after it — running jobs and finished renders keep the intent they already recorded.

The representation default becomes a per-user preference, as the state-ownership audit assigns: the last chosen preset id persists in Rhino's plug-in settings and is restored when its id still exists ("last compatible choice"); a deleted or absent id falls back to the first supplied preset. Choosing a project model or pinning still never reads or writes this preference. The optional prompt field stays per-render and per-session by design.

The store is the deliberate hardening boundary, because these are user-authored strings that reach prompts: every read validates shape and bounds (personal ids are `personal-`-prefixed and can never collide with a supplied id a pin already recorded; names, descriptions, instructions and the two preservation fields have the same bounds `PromptComposer` enforces; passes must stay non-empty), duplicate-JSON-key rejection is shared with every other wire document, a corrupt, oversized or plausibly-modified file fails closed to the supplied presets with the reason named instead of taking the panel or a render down, and writes are atomic (temp file + rename), user-private (0600/0700) and bounded (1 MiB). The panel names a read problem once at startup and the editor repeats it; nothing about the failure disables the supplied presets.

Because the native checks load the plugin sources without a registered plug-in, the fixture's `VisoLoomPlugIn` stub now returns null for `Instance` instead of throwing, so null-guarded preference access — this is the first preference on that path — runs unchanged in the fixture and every accidental dereference still fails loudly.

## Consequences

- A designer can now name and keep their own treatments next to the supplied ones, and Rhino sessions start on the treatment they actually chose last; the personal file is plain JSON a user can inspect or deliberately export, and a fresh install has none.
- Every distinct save of a preset is a new revision; a render's provenance names the exact generation that produced it.
- Six new store tests in Core.Tests cover the round trip with revision stamping, replacement, deletion of a named preset, the fail-closed reads (corrupt, oversized, wrong schema, duplicate ids) including that a failed store cannot be written into blindly, validation rejects unsafe records on save, and atomic writes leave no temporary files behind.
- The editor is necessarily unverified outside the host (Eto dialogs cannot be driven headlessly here): native checks to run are the walkthrough of Edit preset… → Save as new preset… → restart Rhino (the personal preset and the restored default), in-place edit (revision advances), delete (confirmed, selection falls back), and the corrupt-file story. Windows paths remain, as ever.
- The IA's future work list shrinks correspondingly: personal-preset *export/import* and per-project overrides are not included and remain unclaimed.
