# ADR 0026 — xAI account-listed model selection

Status: Owner decision on 2026-11-20 ("implement all the providers; do all the same thing for the other providers as well"). ADR 0024's posture extends to xAI's JSON edit surface from the published documentation — [image editing](https://docs.x.ai/developers/model-capabilities/images/editing), [image generation](https://docs.x.ai/developers/model-capabilities/images/generation), the [REST reference for images](https://docs.x.ai/developers/rest-api-reference/inference/images) and [for models](https://docs.x.ai/developers/rest-api-reference/inference/models), the [models page](https://docs.x.ai/developers/models) and the [quality-model retirement guide](https://docs.x.ai/developers/migration/imagine-image-quality-nov-2) — reviewed 2026-11-20; no live request was made.

## Decision

The connection check keeps every `grok-imagine-image…` model the authenticated `GET v1/models` list offers (bounded like the other lists: 1 MiB of JSON, 1,024 entries), newest first by the listing's documented `created` field, an entry without it last. Text, video and voice models are filtered and a familyless account fails closed as before. The Render panel offers those rows beside the tested `grok-imagine-image-2.0`; Settings owns the xAI API key in the OS credential store under its own origin.

Every sent field is the documented edit request. `POST /v1/images/edits` carries the model, the exact recorded prompt, the inline PNG reference as a data URL, and `response_format: "b64_json"` so the result arrives inline instead of as a hosted link. The 2k output tier is requested first — the biggest documented tier, per the owner's biggest-first posture (ADR 0024) — and an account-listed model that explicitly declines it (an HTTP 400 naming `resolution`, read as bounded JSON) is resubmitted exactly once with the tier omitted, at the documented default, with the decline prepended to the render's history. The tested profile never falls back; ambiguous or other rejections never retry. `aspect_ratio` stays at its documented default `auto`, which follows the source image's ratio; `quality` stays at its documented default, at which edits serve medium; `n` stays at its documented default of one. No value is invented.

The tier names publish no pixel table, so no size is pinned in the request: VisoLoom plans the prepared input canvas on the documented scale — a 16-pixel alignment within a 2k-tier square, the widest accepted ratio 5:2 — and normalizes whatever canvas the model returns back into the complete Rhino frame. Verified per-tier pixel tables remain a promotion path for a compiled tested profile, exactly as for Google (ADR 0025). The `sizeContractUnpinned` gate is retired, superseded by that documented contract.

Two results-side facts from the documentation change shared code. First, the default edit quality serves JPEG, so the Rhino host's result normalization now decodes what actually arrived — any format the host codec supports — instead of asserting a PNG header up front, and always re-encodes the restored frame as PNG; the returned `mime_type` is accepted for the documented image mimes and anything else fails closed. The observed mime is recorded in the render's history when it is not PNG. Provider pipelines never follow a hosted link: a result that arrives as `url` instead of inline bytes fails closed with `urlResultNotSupported`, keeping the 2026-11-10 owner policy ([ADR 0020](0020-google-xai-adapter-scaffolds.md)) — one fetch per job from exactly the approved origin — pending the live-endpoint research that must record the result host, expiry and encoding first. A stray `url` field beside present inline bytes is ignored, not fetched.

The shared flows are unchanged and now cover the third cloud: per-render provenance records the model id as the model and version, the local-history intent records an `xaiCloud` destination, project pins store provider/model/version as before, a document-supplied cloud pin renders only after its explicit in-session choice, and no submission is retried automatically.

Two latent defects from the Google increment were found and fixed while wiring xAI: the render path ran the local-engine destination check on every non-OpenAI job, so a Google render could never start — the loopback endpoint can never equal a cloud origin — and the local history recorded Google renders with a `loopbackReferenceServer` destination. The check now applies only to local and managed jobs, and each cloud records its own destination.

## Consequences

- New Grok Imagine image models are selectable the day the account lists them; retired slugs that xAI still resolves (such as `grok-imagine-image-quality`) keep working by xAI's documented redirect, at xAI's served quality.
- The first real edit may reveal returned canvases that differ from the planned native canvas; such a result fails closed with its provenance recorded, and the live acceptance item stands. JPEG results are the documented default and are expected to work before native testing confirms it.
- The contract-tested provider-catalogue descriptors now state that Google and xAI require an API key and cloud opt-in, matching what the Settings page actually offers; the Core invariant moves with them — the wired clouds are available, only the BFL scaffold stays closed.
- Native Rhino checks — the loaded Settings section, the Model menu with a real account list, and the first live edit through the panel — remain open, as do Windows paths and the recorded URL-result research if the hosted flow is ever wanted.
