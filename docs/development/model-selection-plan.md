# Model selection implementation plan

Start here when implementing the model and Settings workflow. Use the [Settings wireframe](../ux/panel-wireframe.md#model-selector-and-settings) and open the [clickable mockup](../ux/settings-mockup.html) from a checkout in a browser. The [local engine decision](../adr/0022-engine-bundling-and-one-click-model-install.md) defines packaging, storage and the runner boundary. The [local editor research](../providers/local-image-editors.md) records the broader model inventory and comparisons.

## Product behavior

The Rhino panel shows the selected model and where it runs. Settings owns connection checks, account discovery, and local model setup. Preview and Render use the same flow for all providers. Selecting a model or refreshing a connection sends no project data.

OpenAI model selection follows the account list: every image model the account offers is selectable, the catalogue marks which profile the plug-in has tested, and a recommendation change shows before the next preview. An explicit project pin stores the provider, model ID, and version in the Rhino file. A pin restored from a received document is visible immediately, but a cloud destination renders only after an explicit in-session choice; a shared file must not submit through the reader's own account. When a provider only exposes a moving model ID, identify it as such. A missing or retired project pin stays visible and requires an explicit replacement. Later OpenAI snapshots attempt the reviewed custom-size contract first and fall back once onto the family standard canvas on an explicit size rejection, without a per-model gate ([ADR 0024](../adr/0024-account-listed-openai-model-selection.md)); Google follows the account list the same way on its documented request, which carries no size at all ([ADR 0025](../adr/0025-account-listed-google-model-selection.md)); xAI requests its documented 2k tier first and falls back once onto the default tier on an explicit `resolution` rejection ([ADR 0026](../adr/0026-xai-account-listed-model-selection.md)); promoting a snapshot to the compiled tested tier keeps the comparison protocol as adoption evidence. Local installations change through deliberate activation. Settings pairs each local model choice with the one reviewed engine profile it installs toward, and marks the profile the running engine itself reports as connected, so the reviewed FLUX.2 and FLUX.3 profiles stay distinct and no installation is presented as active from file presence alone.

BFL's hosted profile completed on 2026-11-25 ([ADR 0027](../adr/0027-bfl-wired-around-reference-gate.md)'s resolution): FLUX 3 Image Klein is implemented on its documented inline base64 contract. Treat hosted BFL and installed FLUX weights as separate destinations in the Render selector.

## Existing foundation

The panel and `CaptureCoordinator` handle capture tests, connected OpenAI, Google and xAI models, an active local engine, and project model pins. Profile selection keeps the prepared image and prompt tied to the reviewed destination. Settings is one native page shared by Rhino Options and the Render panel. It includes inline provider forms, reviewed model downloads, existing files and image-saving options. Packaging the native runner and connecting to an office server remain separate milestones. [Native Settings layout](../ux/panel-wireframe.md#native-settings-layout)

OpenAI, Google and xAI connection checks discover their account-listed image models. **Refresh models** updates the list with the active key. Black Forest Labs uses its curated hosted list and an API-key check. It can show the available profiles while rendering remains pending.

Keep `RenderModelProfile` and `ResolutionPlanner` as the source for preview, prompt and size limits. Freeze the selected profile, destination, plan, prepared PNG and submitted prompt in the prepared render. Recheck model identity and destination before submission. Preserve single-use preview behavior and capture-test reconnection. Existing history remains readable. Store only provider, model ID and version in a project pin. Keep credentials, paths and endpoints in user settings or their credential namespace.

## Settings and Render share one model list

1. **Connect in Settings.** Open the provider's own row. Check the key and load its usable image-edit profiles. After connection, keep the row open and show **Image models** above **Change API key**. The collapsed row reports **Connected · Key saved**; the key is kept in the OS credential store by default. A connected account with no compatible models says “No supported image models for this account.” Report access and refresh failures in that row. Keep a working key and its model list if a proposed replacement key fails validation.
2. **Resolve availability once.** Use the connection service and provider catalogue to produce one list keyed by exact profile identity. For OpenAI, Google and xAI, intersect account results with reviewed image-edit profiles. **Refresh models** repeats discovery in place without uploading a scene or generating an image. For Black Forest Labs, validate credentials separately and show curated hosted profiles. Credential validation alone provides no model-specific access guarantee. Publish the same resulting list to the Render selector. Use the connected server's capabilities or verified local inventory for those destinations.
3. **Select in Render.** Close Settings with **Done**. Keep the current choice if its exact profile still resolves. If it became unavailable, show its name and direct the designer to reconnect, restore files, or choose another model. On a transient refresh failure, retain the last verified list with the failure shown in Settings. On confirmed access loss or disconnection, remove affected choices from the ready list and keep any affected selection visible as unavailable. Discard responses from older refreshes, replaced credentials or removed connections. After a meaningful change to the selected profile, destination or permissions, invalidate any prepared preview that no longer matches.

## Save a model with a Rhino project

Keep **Project model** with the Render model selector. Use the existing `ProjectModelPin`, `CaptureCoordinator` and `VisoLoomPanel` as the starting point. Settings remains responsible for access on each computer. The project setting records which exact model to try when the file opens on any computer.

| State or action | Expected behavior |
| --- | --- |
| No saved model | Show **Save model with project** for a ready, identifiable model. A “Recommended” or provider-managed choice must resolve to a pinnable profile first. |
| Save or replace | Store the selected provider, model ID and version in `RhinoDoc.Strings`. Mark the document modified and tell the designer to save the Rhino file. Keep API keys, server addresses, tokens and model paths on the machine. |
| Switch model for a render | Change the session choice and invalidate the preview. Keep the saved project model visible. Offer **Replace saved model** to deliberately make the new choice persistent. |
| Open a saved project | Resolve the saved identity against current availability. Select that exact profile when it is ready. If unavailable, show **Unavailable** and the recovery action. Require an explicit choice before rendering with a different profile. |
| Remove saved model | Clear only the document pin. Keep a ready session selection and prompt the designer to save the file. |

Treat a stable revision and a moving alias distinctly. Use only verified revision information and leave a provider-following policy outside the project pin. If a server or package cannot resolve the exact model identity, ask the designer to restore the model or select another one. A catalogue refresh, provider recommendation change or link to a different set of weights must never rewrite a project pin.

Verify with fixtures that model lists feed both surfaces, a failed replacement leaves the active connection intact, and a late refresh cannot restore a disconnected account. Test pin, temporary switch, replace, clear, save and reopen across two documents and on a second installation without the pinned model. In Rhino, verify the save prompt and modified indicator explicitly. The prior native fixture confirmed pin persistence and no automatic fallback, but did not observe the modified indicator.

## Local model controls and scene guidance

Use the Render panel's **View**, **Representation**, **Model**, optional **Prompt**, and **Output size**. Model profiles own seed policy, steps, guidance, sampler, precision, and quantisation. Record the parameters the runner used with the result. Keep those settings out of the initial designer UI. Revisit an individual control if it makes a clear architectural choice possible and its effect is supported by the selected profile.

1. **Start with the captured view.** Use Rhino's display style, camera, materials, and section state to make the source legible. Keep the complete scene package locally for inspection and framing. Retain the source as the comparison image for the result.
2. **Use a concise local prompt.** FLUX.2 klein 4B starts with one prepared PNG, the representation instruction, one preservation instruction and the designer's optional prompt. A useful clarification is “Keep the board-formed concrete on the entrance wall.” The current MFLUX recipe checks 2,048 UTF-8 bytes and 512 tokens after formatting. Show a clear shorten-prompt action when validation fails. Leave the `.3dm`, layer inventory, material file paths and approximate colour swatches out of this recipe.
3. **Prepare text by profile.** For local FLUX 3 Image Klein, validate the image pipeline with an authored full caption first. Qualify a local captioning step for routine use, with its weights, memory and exact caption recorded. Keep the same reference throughout. For hosted FLUX 3 Image Klein, the BFL service expands the instruction. Show the submitted prompt as such in Preview, and record the provider-expanded text only if BFL supplies it. Preserve the currently implemented OpenAI context and privacy choices until a separate comparison supports changing them.
4. **Make the input inspectable.** Scene guidance is a collapsed summary of what the selected profile will receive. Preview shows the prepared frame and allows viewing its exact submitted prompt. If the image, model, destination, permissions or prompt change, require an updated preview. Research additional material context using the same view and text with and without a small set of reliably located cues. Consider aligned depth or edges only for a profile that consumes them. Compare built geometry and appearance across the whole view before adopting the extra input. [Material context research](../architecture/material-appearance.md) · [Local prompt decision](../adr/0017-local-inference-and-model-prompts.md)

## Availability and updates

1. Add per-provider connection settings and credential namespaces when each provider is wired in. Migrate the existing OpenAI settings without granting any new cloud permission. Refresh access on connect and on demand. Cache results by connection, discard stale responses after credential replacement, and retain the last known status on transient failures. Model listing establishes access evidence. Format, size, and request support come from a reviewed adapter profile.
2. Ship a bundled compatibility catalogue first. Add a signed, versioned update channel when there is a second supported cloud profile to maintain. Validate schema, signature, revision, and required adapter version before atomically replacing the last good copy. Limit updates to model IDs, profile references, labels, recommendation and retirement data. Compiled adapters own endpoints, credentials, request and disclosure behavior, and hard byte and pixel ceilings. Use only VisoLoom's public catalogue URL for refresh. No model access details or scene data go to it.
3. Keep credentials in the OS credential store by default ([ADR 0031](../adr/0031-consent-on-connect.md)): entering a key and connecting is the consent to render; the provider row keeps stating what its render request transmits, and forgetting the key is the explicit action. On failure retain the user's model choice. A billable submission that times out or has unknown completion is never automatically retried. An approved async job may continue bounded status polling by job ID. Where remote cancellation is unavailable, label the control **Stop waiting**.

## Release checks

Use independent fixtures for model availability and retirement, malformed capabilities, connection replacement, old documents and history, pin/reopen, stale preview, and failure before or after a potentially billable submission. Verify no image submission on preview, model checks, or provider switches. Exercise narrow and docked panels in Rhino on supported hosts. For new render profiles, use identical authored façade, section/stair and material/planting captures to compare framing, openings, proportions and material placement, as well as latency and cost.

Reuse the existing Core and Protocol suites, `tests/engine`, and the native Settings, panel and preview fixtures in `tests/native`. The [Rhino smoke test](plugin-smoke-test.md) describes host setup. Before release, confirm the native runner build, redistribution review, usable GPU memory with Rhino open, clean installation and cancellation on each platform. Confirm each cloud profile with a deliberate, authorised edit using a non-confidential fixture. The handoff specifies these validation jobs. Their results determine release readiness and hardware recommendations.
