# Rhino 8 feasibility and evidence

Review date: 2026-09-19. Status: documentation research and local SDK inspection only. API availability is not an in-host behavior test.

The proposed runtime baseline below is historical. On 2026-10-11 the user clarified a target covering the Rhino 8 series; [ADR 0010](../adr/0010-rhino-8-series-compatibility.md) replaces the minimum with the original 8.0 SDK and a .NET 7 assembly compatible with Rhino's later .NET 8 hosts. The current slice compiles against that SDK; native validation remains open.

## Evidence sources

Official current guides were checked alongside the installed Rhino 8.16 XML documentation at `/Applications/Rhino 8.app/Contents/Frameworks/RhCore.framework/Versions/A/Resources/RhinoCommon.xml`. XML member summaries and `since` tags confirm symbols in that installed SDK; newer online docs can describe newer service releases. Pin the actual minimum SDK during the approved scaffold and inspect every newer API used.

| Area | Verified API / documented behavior | Proposed use and outstanding limitation |
| --- | --- | --- |
| Plug-in architecture | RhinoCommon is the .NET SDK; command plug-ins are supported on Mac. [Guides](https://developer.rhino3d.com/guides/rhinocommon/), [Mac plug-in guide](https://developer.rhino3d.com/guides/rhinocommon/your-first-plugin-mac/) | Standard plug-in with two commands; no rendering engine needed for the first slice. |
| Render engine | Installed `RenderPlugIn.Render` is invoked for Rhino Render/RenderPreview when selected as default renderer. [API](https://developer.rhino3d.com/api/rhinocommon/rhino.plugins.renderplugin) | The extra renderer lifecycle/content/settings integration has no demonstrated first-slice benefit. Revisit only for a concrete need for Rhino's rendering workflow. |
| Runtime / both OSs | Rhino 8 moved to .NET Core; `net8.0` is recommended and default from 8.20. Earlier releases differ. [Runtime guidance](https://developer.rhino3d.com/guides/rhinocommon/moving-to-dotnet-core/) | Propose Rhino 8.20+, .NET 8 selected, managed AnyCPU. No `net48`, WPF, or WinForms dependency. Runtime servicing risk is in the technical review. |
| Apple Silicon | McNeel specifies AnyCPU managed assemblies; native dependencies require compatible architecture builds for the supported Macs. [Runtime guidance](https://developer.rhino3d.com/guides/rhinocommon/moving-to-dotnet-core/) | Run on native arm64; avoid native packages in the first slice. Windows x64 is a separate test environment. |
| Eto UI | Eto panels work on both platforms; per-document panels and Mac inspector lifetimes differ. [Tabbed panels](https://developer.rhino3d.com/guides/rhinocommon/tabbed-panels/), [Eto guides](https://developer.rhino3d.com/guides/eto/) | Jobs cannot belong to one singleton panel instance. Bind document explicitly; unsubscribe events on disposal. |
| View capture | `ViewCapture` has pixel width/height, adornment flags, transparency and realtime-pass settings; `CaptureToBitmap` overloads and `CaptureToSvg` exist. [API](https://developer.rhino3d.com/api/RhinoCommon/html/T_Rhino_Display_ViewCapture.htm) | Reference capture first; test DPI scaling, PNG encoding, screen-item scaling, grids and selection appearance. A capture is synchronous host work. |
| Offscreen capture | Installed `DisplayPipeline.DrawToBitmap(viewport,width,height)` exists. | Candidate for a copied viewport. It does not prove every display mode, third-party conduit, or clip participation survives a copied viewport ID. Test before use. |
| Named Views | Rhino saves/restores views; modified views have a visible indicator and aspect restoration is optional. Installed table APIs include `RestoreWithAspectRatio`. [NamedView](https://docs.mcneel.com/rhino/8/help/en-us/commands/namedview.htm) | Capture the actual active viewport. A remembered name alone cannot identify the current frame. No VisoLoom Named View table. |
| Camera and projections | Installed viewport APIs expose camera frame, frustum, projection flags, transforms, frustum lines and pixel size. `GetTransform` can return identity on failure. | Persist the full view projection. Validate camera/frustum, near/far, matrix convention, and two-point perspective. Never synthesize a second camera per pass. |
| Display modes | Installed `DisplayModeDescription.GetDisplayModes` enumerates current modes. Rhino has built-in and custom modes. | Default to the user's mode. Only offer source modes present in this host. Raytraced/third-party mode capture and convergence are untested; fail or offer an explicit alternative, never substitute silently. |
| Conduits | Rhino exposes drawing/culling events; ordering between other active conduits is not guaranteed. [Display conduits](https://developer.rhino3d.com/guides/rhinocommon/display-conduits/) | Scope custom generators tightly to capture/document/viewport. Restore/disable in `finally`. Foreign preview geometry may appear in reference without object/material metadata. |
| Object display overrides | Installed `ObjectAttributes.SetDisplayModeOverride` supports viewport-specific overrides. | Availability is not permission to mutate the model for export. Prefer isolated capture attributes/conduits; verify no document-dirty or undo side effects. |
| Material access | Installed `RhinoObject.GetRenderMaterial` and `GetMaterial` support object/subcomponent lookups; render material can be null. Layer render material/index and material-source settings exist. [Material API](https://mcneel.github.io/rhinocommon-api-docs/api/RhinoCommon/html/Overload_Rhino_DocObjects_RhinoObject_GetRenderMaterial.htm) | Resolve object/layer/default/front/back and instance/subobject cases with provenance. Null does not mean “no appearance.” Name parsing alone is insufficient. |
| PBR and custom materials | Installed PBR fields include base color, roughness, metallic, opacity and IOR; render materials support simulation to a basic material. | Extract only applicable values. Legacy shine is not automatically roughness. Custom procedural/renderer materials may need approximate summaries; do not bake textures or upload paths by default. |
| Visibility | Object hidden state, layer visibility, and view/clipping state affect capture; locked objects can remain visible. | Eligible scene objects are not the same as pixel-visible objects. Test nested layers, blocks, per-view settings and occlusion; disclose incomplete metadata. |
| Clipping | `ClippingPlaneSurface.ViewportIds`, depth properties and participation-list APIs exist in installed SDK. [ClippingPlane](https://docs.mcneel.com/rhino/8/help/en-us/commands/clippingplane.htm) | Capture per-view plane participation, direction, enabled finite depth and inclusion/exclusion. A plane widget's rectangle is not the section boundary. |
| Section geometry | Installed `RhinoObject.GetFillSurfaces` overloads return possible cut fills and can trim against other planes. `Intersection.BrepPlane`/`MeshPlane` return section curves. | Investigate native fill surfaces first. Intersections alone do not solve visible-mask occlusion, holes, multiple planes or open geometry. No universal section-mask guarantee. |
| Depth | `ZBufferCapture` exposes `ZValueAt`, `WorldPointAt`, extrema and grayscale preview. [API](https://developer.rhino3d.com/api/rhinocommon/rhino.display.zbuffercapture) | Direct API exists. Establish units, sign, background, viewport sizing, high-resolution capture and clipping. Do not rescale a low-resolution Z buffer and call it aligned high-resolution depth. |
| Normals | Installed mesh vertex/face normals, `Surface.NormalAt`, and false-color mesh drawing exist. | No verified turnkey visible normal-buffer export in this review. Custom tessellated capture is possible in principle but must match occlusion and Rhino shading; defer. |
| Technical/vector output | `CaptureToSvg` and technical display are available; display-mode/conduit extraction can provide lines. | First investigate texture-free structural display capture. Make2D/vector output is not automatically a pixel-aligned control pass. Tessellation wires and vegetation mesh noise should not dominate. |
| ID passes | Installed false-color mesh draw and display hooks provide building blocks. | No verified one-call material/object/semantic-ID exporter. Disable antialiasing, blending and color conversion, resolve materials before drawing, and validate frontmost coverage. Deferred. |
| Threading | Installed `RhinoApp.InvokeOnUiThread` marshals work to the UI thread. | Keep Rhino document/display access on that thread; worker tasks use detached values/owned bytes. UI dispatch does not make capture itself nonblocking. |
| Yak | Local package creation/installation and platform/distribution tags are documented. [Package structure](https://developer.rhino3d.com/guides/yak/the-anatomy-of-a-package/), [CLI](https://developer.rhino3d.com/guides/yak/yak-cli-reference/) | Use a local prerelease package; no public push. Encode minimum service release in distribution tags. Do not bundle Rhino host assemblies or any ML runtime. |

## Pass plan

Reference capture is the first implementation candidate. Next investigate structural edges and material IDs because they directly support architectural use. Depth is worth an early feasibility experiment, but generation stays unavailable until alignment and metric encoding are tested. Semantic/object IDs can reuse a proven categorical pass pipeline later. Normal and section-mask production support are deferred.

If Z-buffer capture cannot match the required output, retain protocol support and investigate per-pixel intersections with captured render meshes using the same frustum rays. That alternative has real complexity: transparency, clipping participation, instances, tessellation and performance. Do not implement it merely to fill a field. A copied viewport that loses active clipping is also not a valid substitute.

## Experiments after approval

1. Build/load a minimal command and Eto panel on supported Rhino for macOS arm64 and Windows; close/reopen panel and document during an outstanding job.
2. Capture a synthetic asymmetric frame with openings at all borders, in perspective/parallel/two-point and odd resolutions; compare source framing at 1×/2×/4× and verify zero camera/document mutation.
3. Test current Shaded, Rendered, Arctic, Technical/Pen where present, custom modes, grids, selected objects, clipping widgets and a foreign conduit. Record exclusions rather than promising all display effects.
4. Test simple/layer/default materials, procedural materials, backfaces, nested blocks with parent material, subobject assignments, hidden layers and per-view visibility. Compare eligible metadata with actual pixels.
5. For future maps, test holes, transparent glazing, overlapping geometry, multiple clipping planes, finite depth and participation exclusions. Measure border registration and validate categorical pixel values.
6. Measure capture stalls and peak memory at realistic dimensions. A 4096 × 2304 RGBA buffer alone is about 36 MiB; multiple passes and copies multiply this. Keep only the buffers required by the active generator.

No results from these experiments are claimed in Phase 0. Current environment specifics are recorded in [DEVELOPMENT.md](../../DEVELOPMENT.md).
