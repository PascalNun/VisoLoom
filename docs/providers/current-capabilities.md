## BFL / FLUX

**Wired, unrenderable by decision.** `BflImageProvider` targets `https://api.bfl.ai/` with `x-key` authentication. The connection check validates the key against the documented credits endpoint; the Model menu offers the documented curated pair — `flux-2-pro` (pinned, BFL's recommended default) and `flux-2-pro-preview` (the moving preview) — on the documented pro contract (width and height ≥ 64, up to the 4 MP family claim). Rendering fails closed on `referenceUploadUnresolved`: the published schema takes hosted image-URL references only, the endpoint index documents no upload or base64 surface, and VisoLoom hosts no images — how a reference would ever reach BFL is an open decision ([ADR 0027](../adr/0027-bfl-wired-around-reference-gate.md)). The async submit/poll flow and the expiring result download are deliberately not implemented behind that gate, so no image is sent, no reference host is contacted, and no billing can occur.
Recorded for that open decision: the public BFL schema checked on 2026-11-20 documents one or more base64 or URL references through `images` on the hosted `/v1/flux-3-image-klein` endpoint — a different surface from the curated FLUX.2 pro pair, and a documented route for sending a single prepared PNG without hosting the source separately. BFL runs prompt upsampling and defaults an edit to the first reference's size. [BFL OpenAPI schema](https://api.bfl.ai/openapi.json) · [FLUX 3 Image Klein review](flux3-klein.md)

The current FLUX.2 editing guide distinguishes up to **8 API references** from 10 playground images, describes output up to **4 MP**, and returns an ID/polling URL. Output URLs expire after ten minutes. `x-key` authentication and image-URL inputs are documented. Prefer a stable model such as `flux-2-pro` over the moving preview endpoint for a reproducible integration baseline. [Editing guide](https://docs.bfl.ai/flux_2/flux2_image_editing).

The pro endpoint exposes width/height (documented minimum 64), optional seed, PNG/JPEG/WebP, optional webhooks, and cost/input/output-megapixel fields. Its schema does not fully specify the maximum dimensions, multiples or aggregate upload limits. Base64 acceptance also remains unresolved in that selected schema. Do not substitute a family-level assumption for these gaps. Automatic prompt expansion is enabled by default; the proposed adapter should use `disable_pup` to retain the effective prompt VisoLoom records. [FLUX.2 pro API](https://docs.bfl.ai/api-reference/models/generate-or-edit-an-image-with-flux2-%5Bpro%5D).

FLUX.2 and earlier FLUX Fill/Canny/Depth endpoints must not be conflated: a separate controlled model is not evidence that ordinary FLUX.2 reference inputs accept those controls. [Official endpoint index](https://docs.bfl.ai/llms.txt).

No confirmed cancellation or deterministic geometry guarantee was established for the proposed pro editing adapter. Until verified, use client-only stop-waiting semantics. Pricing varies by model and processed input/output; store dated estimates rather than one “FLUX price.” [BFL pricing](https://bfl.ai/pricing).

## OpenAI

Implemented profile: `gpt-image-2.5-sunburst-2026-09-08`, direct JSON `/v1/images/edits`, one reference/output, PNG, opaque background, medium quality. Application caps: prepared input 14 MiB, output 32 MiB and response JSON 45 MiB. Model selection follows the authenticated `GET /v1/models` account list (bounded to 1 MiB and 1,024 entries, family-filtered, newest first): the tested snapshot keeps its reviewed custom sizes, and every later image model the account offers is selectable; it plans on the reviewed custom-size contract first and falls back once onto the standard canvas set (1024×1024, 1024×1536, 1536×1024) when the reply names `size` as rejected ([ADR 0024](../adr/0024-account-listed-openai-model-selection.md)). The snapshot id is the recorded model version. No `input_fidelity` flag is sent: its documented applicability must not be assumed for this snapshot. The exact composed context, source hash, native/final plan and result hashes are recorded. The Mac padding/export path has live evidence; native resampling and Windows acceptance remain open. Local preview now freezes the prepared model PNG and prompt before submission; see [ADR 0015](../adr/0015-preview-before-submission.md). See [ADR 0012](../adr/0012-first-openai-image-edit.md).

The current guide covers `gpt-image-2.5-sunburst` and `gpt-image-2.5-flare`; editing precision makes Sunburst a candidate for evaluation. Direct Image API edits fit one-shot VisoLoom requests. Current custom-size rules include multiples of 16, ratios from 1:3 to 3:1, maximum edge 3840, and 655,360–8,294,400 pixels; above 2560 × 1440 is experimental. PNG/JPEG/WebP and transparency options are documented. Masks guide edits but do not enforce exact boundaries. [Image guide](https://developers.openai.com/api/docs/guides/image-generation).

The edit reference lists up to 16 inputs, 1–10 results, optional high/low input fidelity, partial-image streaming, and dated September 8 model snapshots. JSON URL/data inputs have a 20,971,520-character limit per URL field. The guide separately describes image/mask uploads below 50 MB; request encoding and endpoint-specific limits need validation rather than treating these numbers as equivalent. Start with one input/output and conservative application caps. [Edit reference](https://developers.openai.com/api/reference/resources/images/methods/edit).

Bearer API-key authentication is documented in the guide's HTTP examples. No server-side cancellation contract for the direct Image API was established; do not assume Responses cancellation applies to it. Pricing is model/quality/size dependent, with token accounting; this adapter uses separate API billing. The newer [Sign in with ChatGPT](https://developers.openai.com/siwc/quickstart) supports plan usage for eligible requests, but its [current limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) explicitly exclude image generation; account login is not a supported replacement for this image-editing connection. [Pricing](https://developers.openai.com/api/docs/pricing).

## Google / Nano Banana — reviewed 2026-10-12

**Implemented, account-listed.** `GoogleImageProvider` targets the Interactions surface (`/v1beta/interactions`, `x-goog-api-key`) with one inline PNG reference and the exact recorded prompt. Selection follows the authenticated `models.list` results (family-filtered, bounded, provider order); the tested snapshot `gemini-nano-banana-2.1` keeps its row, any later listed image model is selectable on the documented contract. Since 23.11.2026 the canvas is planned locked to one of the aspect ratios the model pages name (ten shared values), the request names that same ratio through `response_format.aspect_ratio`, and a returned canvas at the command's own extent restores as the same drawing rescaled — a reframed canvas still fails closed ([ADR 0025](../adr/0025-account-listed-google-model-selection.md)). The `image_size` strings conflict between the general guide (`1K`, `2K`, `4K`) and the Lite model page (`1024px`), so no tier is sent: the documented default applies. Verified per-tier values remain a promotion path to a compiled tested profile.

The current guide identifies `gemini-nano-banana-2.1`, Pro `gemini-3-pro-image`, Lite and older Flash variants. Text/image editing and conversational revision are supported. Applicable models accept multiple references and model-specific 1K/2K/4K tiers with discrete pixel tables, not arbitrary output sizes. Images include SynthID. Its current examples use Interactions (`/v1beta/interactions`) with `x-goog-api-key` and the `Api-Revision: 2026-05-20` header; `response_format` carries the image's mime, `aspect_ratio` and `image_size`; do not copy generateContent payloads into that surface. The **response schema restructured in May 2026** and the legacy shape was removed on 8 June 2026: an accepted reply now nests `steps[] → a model_output step → content[]`, and the image part there carries `mime_type` and `data` (the SDK's `output_image` is sugar over it). The adapter parses that shape and pins the revision header. [Image guide](https://ai.google.dev/gemini-api/docs/image-generation), [migration guide](https://ai.google.dev/gemini-api/docs/interactions-breaking-changes-may-2026).

The owner's live incident on 23.11.2026 — `gemini-3.1-flash-lite-image` refusing every request with HTTP 400 — is pinned by the machine-local rejection log on 24.11.2026: **the Lite model supports only `image/jpeg` output**, and the request's `response_format.mime_type` named `image/png`. Every request on that model failed the same way from the first incident; the managed models also name their machine reason as `error.code` (`invalid_request`), not `error.status`. The family now requests JPEG outright: a second model, `gemini-3.1-flash-image-preview`, refused PNG with the identical machine reason on 25.11.2026 — the generation surface's own answer, not the general guide's stale PNG row, is the contract. The reply's declared JPEG is decoded and the frame restored as PNG exactly as xAI's JPEG path does, and the status line surfaces `error.status` **or** `error.code`. A future refusal of this kind follows the same loop: the log records it, the model's contract entry gets updated — nothing ships from a licence or acceptance event, only from the provider's own recorded statement. [Lite model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-lite-image).

Some table headings and model names differ; verify the selected endpoint before pinning capabilities. Plan using actual pixels, not a nominal ratio label. No exact geometry or native Rhino-map control contract was established.

Inline input is bounded at 20 MB including text/bytes; Files input needs a separate retention review. [Image input](https://ai.google.dev/gemini-api/docs/image-understanding). Check the chosen account's paid/free data policy and image pricing before confidential use. [Pricing/tier information](https://ai.google.dev/gemini-api/docs/pricing).

Interactive and batch lifecycle contracts differ; batch cancellation does not establish interactive cancellation. [Batch API](https://ai.google.dev/gemini-api/docs/batch-api).

## xAI / Grok Imagine — reviewed 2026-10-12

**Implemented, account-listed.** `XaiImageProvider` targets the JSON edit surface (`/v1/images/edits`, bearer keys, one inline PNG reference). Selection follows the authenticated `v1/models` results — every `grok-imagine-image…` id, newest first by the documented `created` field; the tested `grok-imagine-image-2.0` keeps its row. The request carries exactly the documented fields: inline result format, the 2k tier first with one fallback onto the default tier on an explicit `resolution` rejection, the canvas's documented `aspect_ratio` since 23.11.2026, and documented defaults for quality (medium for edits) and count ([ADR 0026](../adr/0026-xai-account-listed-model-selection.md)). The default edit quality serves JPEG, so the host decodes the returned mime and re-encodes the restored frame as PNG; hosted link results still fail closed with `urlResultNotSupported` pending the decided download policy's research. Per-tier pixel tables remain a promotion path.

The owner's live incident on 23.11.2026 drove the `aspect_ratio` change: `grok-imagine-image` answered a planned 2,048 × 1,516 canvas with a 2,048 × 1,808 image — an aspect the request never named — and the frame restore failed closed while the generation was charged. The request now names the planned ratio, and a return at the command's own extent restores as the same drawing rescaled; a reframed return still fails closed with the structured `error.type` in the status line.

Current docs use `grok-imagine-image-2.0`, with `/v1/images/edits`, bearer API keys, and URL/base64/File-ID inputs. [Editing](https://docs.x.ai/developers/model-capabilities/images/editing). Multi-image edits accept up to five inputs and default to the first input's ratio; an explicit supported ratio can override it. That does not establish exact arbitrary-size preservation. [Multi-image editing](https://docs.x.ai/developers/model-capabilities/images/multi-image-editing).

Generation docs expose selected aspect ratios, 1K/2K resolution tiers, up to ten outputs and URL/base64 responses. Generation also exposes quality controls; this is not proof that the edit surface accepts every generation option. Confirm edit controls and decoded dimensions before advertising them. URL responses and examples using JPEG mean the adapter must decode the actual format and normalize to PNG, rather than assume PNG bytes. No arbitrary pixel-size, exact mask, depth/semantic control, percentage progress, or confirmed remote image-cancellation guarantee was established in the reviewed edit surface. [Generation](https://docs.x.ai/developers/model-capabilities/images/generation).

The documentation also has a dated retirement notice for an older image-quality model. Model catalogue changes need explicit migration, not a silent default swap. [Retirement notice](https://docs.x.ai/developers/migration/imagine-image-quality-nov-2), [models and pricing](https://docs.x.ai/developers/models).

## Machine-local rejection log — 23.11.2026

A provider refusal is bounded twice over: the status line keeps only the structured machine reason (`error.status` for Google, `error.type` for xAI), and the provider's own rejection body — read only on the failure path, capped at 8 KB — now rides on the `ProviderException`. The host writes each recorded refusal to `provider-rejections.jsonl` under the app data root, beside the model library (`~/.local/share/VisoLoom/logs` on macOS and Linux, `%LocalAppData%\VisoLoom\logs` on Windows): time, provider, model, the honest status sentence and the bounded body, one JSON line per event, the file capped at 256 KB keeping its recent tail. The log is diagnostics material owned by the machine's user; it is not a message surface, and no user-facing sentence reads it. OpenAI's and BFL's adapters do not read rejection bodies today, so they log the sentence only.

## Model lists persist and refresh at session start — 23.11.2026

The account model lists — the Model menu's source — now persist in the local settings store after each successful discovery and load immediately at startup, so a fresh Rhino session shows each connected provider's models without a Settings visit. Every session refreshes each connected provider's list once in the background (`AccountListRefresh`, 15-second bound, silent failure keeps the persisted list); Rhino's start and each panel open ask for the pass, and the first pass that publishes any provider's list rests the session. Disconnecting a provider clears its persisted list with its key. The manual per-provider refresh in Settings stays: it is the place a failure's reason is read.
